Memory & errors

A multi-GB model on a phone lives or dies by memory. The guiding principle: an on-device LLM that fails to load with a clear error is recoverable — an OS kill (iOS jetsam, Android LMK) is not. This page covers the estimator, forecasts, budgets, OS pressure warnings, tracking, teardown, and the typed errors that tie them together.

Pre-flight estimation

estimateMemory answers "will this model fit?" before you spend bandwidth downloading it or risk a crash loading it. It is pure and deterministic — deliberately conservative math, no side effects.

function estimateMemory(inputs: MemoryEstimateInputs): MemoryEstimate

loadModel() runs this automatically (see below). Call it directly to drive a model-picker UI before downloading anything.

MemoryEstimateInputs

FieldTypeMeaning
modelFileSizeBytesnumberSize of the .litertlm file on disk, in bytes.
availableMemoryBytesnumberAvailable memory reported by the OS (jetsam-aware on iOS), in bytes.
config?LLMConfigThe load config (backend, maxContextTokens, …).
kvCacheBytesPerTokenOverride?numberOverride the per-token KV-cache cost in bytes (e.g. from calibration). Defaults to a heuristic derived from the model file size.

MemoryEstimate

All values are in bytes.

FieldTypeMeaning
modelBytesnumberModel weights resident in memory (file size × backend load factor).
kvCacheBytesnumberKV cache at full context (maxContextTokens × per-token cost).
overheadBytesnumberRuntime + activation overhead.
totalEstimatedBytesnumberSum of the above — expected peak while the model is loaded.
availableBytesnumberAvailable memory headroom reported by the OS at estimate time.
headroomBytesnumberavailableBytes − totalEstimatedBytes (negative = expected to not fit).
usageFractionnumberFraction of available memory the load would consume (0–∞).
verdictMemoryVerdict'safe' — total ≤ SAFE_FRACTION × available. 'tight' — fits, but with little slack; expect pressure warnings. 'critical' — total exceeds available memory; load will likely crash.
recommendationstringHuman-readable explanation and suggested remediation.
kvCacheBytesPerTokennumberKV-cache cost per token used for this estimate (bytes).
maxContextTokensnumberContext budget (tokens) used for this estimate.

The formula

The math is simple enough to reason about:

  • modelBytes = fileSize × loadFactor — GPU/NPU backends use GPU_LOAD_FACTOR, otherwise CPU_LOAD_FACTOR.
  • kvCacheBytes = maxContextTokens × kvBytesPerToken — halved when config.activationDataType === 'f16'.
  • overheadBytes = max(OVERHEAD_MIN_BYTES, modelBytes × OVERHEAD_WEIGHTS_FRACTION) — i.e. at least 200 MB, or 10% of weights.
  • Verdict: usageFraction ≤ 0.8 → 'safe'; ≤ 1 → 'tight'; else 'critical'.

The constants are exported so tests and calibration scripts can assert against — and document — the exact formula:

typescript
export const ESTIMATOR_CONSTANTS = {
  /** Weights load factor: CPU maps the file plus runtime copies */
  CPU_LOAD_FACTOR: 1.1,
  /** Weights load factor: GPU keeps a device-memory copy alongside staging */
  GPU_LOAD_FACTOR: 1.3,
  /** KV-cache heuristic: bytes per token per GiB of model file */
  KV_BYTES_PER_TOKEN_PER_GIB: 12 * 1024,
  /** KV-cache per-token floor (tiny models still pay layers × heads) */
  KV_BYTES_PER_TOKEN_MIN: 8 * 1024,
  /** KV-cache per-token ceiling (GQA keeps caches small on big models) */
  KV_BYTES_PER_TOKEN_MAX: 96 * 1024,
  /** Fixed runtime overhead floor (engine, tokenizer, buffers) */
  OVERHEAD_MIN_BYTES: 200 * 1024 * 1024,
  /** Activation overhead as a fraction of weights */
  OVERHEAD_WEIGHTS_FRACTION: 0.1,
  /** Verdict boundary: ≤ this fraction of available memory is 'safe' */
  SAFE_FRACTION: 0.8,
  /** Default context budget when the config does not specify one */
  DEFAULT_MAX_CONTEXT_TOKENS: 4096,
} as const;

The per-token KV-cache heuristic is exposed on its own — it clamps (fileSize / GiB) × 12 KiB to the [8 KiB, 96 KiB] range, and you can override it per call from calibration data:

function estimateKvCacheBytesPerToken( modelFileSizeBytes: number, ): number

Example: pick a model before downloading

Estimate against known file sizes and the device's live headroom, and only offer models the device can actually run:

typescript
import {
  createLLM,
  estimateMemory,
  GEMMA_4_E2B_IT,
  GEMMA_4_E4B_IT,
} from "react-native-litert-lm";

const llm = createLLM();
const { availableMemoryBytes } = llm.getMemoryUsage();

const candidates = [
  { name: "Gemma 4 E2B", url: GEMMA_4_E2B_IT, sizeBytes: 2.58e9 },
  { name: "Gemma 4 E4B", url: GEMMA_4_E4B_IT, sizeBytes: 3.65e9 },
];

const options = candidates.map((m) => ({
  ...m,
  estimate: estimateMemory({
    modelFileSizeBytes: m.sizeBytes,
    availableMemoryBytes,
    config: { backend: "cpu", maxContextTokens: 4096 },
  }),
}));

// Hide anything that would likely crash on load
const runnable = options.filter((o) => o.estimate.verdict !== "critical");

Automatic pre-flight in loadModel

The loadModel() on a createLLM instance runs the estimate automatically after resolving (and, if needed, downloading) the model. On a 'critical' verdict it throws a MemoryError instead of loading — unless you pass forceLoad: true in the config. The error message follows this pattern:

error message
Refusing to load model (<N> MB): <recommendation> Pass { forceLoad: true } to override.

Catch it with the isMemoryError type guard — the full MemoryEstimate is attached, so you can show the math and remediate: lower maxContextTokens (the biggest memory lever) or fall back to a smaller model.

typescript
import { createLLM, isMemoryError, GEMMA_4_E4B_IT, GEMMA_4_E2B_IT } from "react-native-litert-lm";

const llm = createLLM();

try {
  await llm.loadModel(GEMMA_4_E4B_IT, { maxContextTokens: 8192 });
} catch (e) {
  if (isMemoryError(e)) {
    console.warn(e.estimate.recommendation);
    console.warn(`short by ${-e.estimate.headroomBytes} bytes`);

    // Remediation 1: shrink the KV cache
    await llm.loadModel(GEMMA_4_E4B_IT, { maxContextTokens: 2048 });

    // Remediation 2: fall back to a smaller model
    // await llm.loadModel(GEMMA_4_E2B_IT);
  } else {
    throw e;
  }
}
forceLoad

forceLoad: true skips the check entirely and loads even when the estimate says the model likely does not fit. It is JS-side only — the native engine ignores the field. Expect an OS kill if the estimate was right.

Forecasting context growth

Once a model is loaded, the KV cache grows with every turn. Forecasting answers "how much longer can this conversation run?" by combining the engine's token count with the KV-cost model.

function forecastMemory(inputs: MemoryForecastInputs): MemoryForecast

On a createLLM instance, getMemoryForecast() does the wiring for you — it reads getContextTokenCount() and the active config, and returns null if no model is loaded. The useModel hook refreshes its memoryForecast after each generate() call.

getMemoryForecast: () => MemoryForecast | null

MemoryForecastInputs

FieldTypeMeaning
contextTokensUsednumberCurrent KV-cache token count from getContextTokenCount() (−1 if unknown).
maxContextTokensnumberContext budget in tokens.
kvCacheBytesPerTokennumberPer-token KV-cache cost in bytes.
warnAtFraction?numberFraction of the context at which nearingLimit flips (default 0.8).

MemoryForecast

All byte values are estimated; token counts come from the engine.

FieldTypeMeaning
contextTokensUsednumberTokens currently in the conversation KV cache.
maxContextTokensnumberContext budget in tokens.
contextUsedFractionnumbercontextTokensUsed / maxContextTokens (0–1).
remainingTokensnumberTokens left before the context window is exhausted.
kvCacheBytesUsednumberEstimated KV-cache bytes currently allocated.
kvCacheBytesRemainingnumberEstimated additional bytes if the context fills completely.
nearingLimitbooleanTrue when contextUsedFraction ≥ warnAtFraction.
Token counts

Token counts are exact on iOS (read from the engine) and approximated on Android, where the SDK does not expose tokenizer counts.

typescript
const forecast = llm.getMemoryForecast();
if (forecast?.nearingLimit) {
  // Summarize the conversation, or warn the user before the window runs out
}

Budgets

A budget turns raw usage into a level. It is expressed as fractions of total (available + used) memory consumed by the process:

export interface MemoryBudget { /** Fire a 'moderate' budget warning at this usage fraction @default 0.75 */ warnAtFraction?: number; /** Fire a 'critical' budget warning at this usage fraction @default 0.9 */ criticalAtFraction?: number; } export type BudgetLevel = "ok" | "warn" | "critical"; function evaluateBudget( residentBytes: number, availableMemoryBytes: number, budget?: MemoryBudget, ): BudgetLevel

evaluateBudget is pure — the fraction it compares against the thresholds is residentBytes / (residentBytes + availableMemoryBytes), and the caller decides how to react. The createLLM wrapper does this for you: pass memoryBudget with an onBudgetExceeded callback, and it evaluates every recorded snapshot, firing the callback on level transitions (ok→warn, warn→critical, …) rather than on every snapshot.

typescript
const llm = createLLM({
  memoryBudget: {
    warnAtFraction: 0.75,
    criticalAtFraction: 0.9,
    onBudgetExceeded: (level) => {
      if (level === "critical") llm.unload();
    },
  },
});

Live usage & OS pressure

getMemoryUsage() reports real memory consumption from OS-level APIs — measured, not estimated.

getMemoryUsage(): MemoryUsage

MemoryUsage

FieldTypeMeaning
nativeHeapBytesnumberNative heap allocated bytes (Debug.getNativeHeapAllocatedSize on Android, malloc_size on iOS).
residentBytesnumberTotal process resident set size (RSS) in bytes.
availableMemoryBytesnumberAvailable system memory in bytes.
isLowMemorybooleanWhether the system considers memory low.

OS memory-pressure warnings

setMemoryWarningCallback( onWarning: (level: MemoryWarningLevel, usage: MemoryUsage) => void, ): void clearMemoryWarningCallback(): void

The callback fires when the OS signals memory pressure — onTrimMemory on Android, the dispatch memory-pressure source on iOS. MemoryWarningLevel has two values: 'moderate' (the system is under pressure; consider freeing caches) and 'critical' (the app is close to being killed; free memory now). Only one callback is active at a time — registering a new one replaces the previous.

On Android the library also releases the engine itself in a genuine memory emergency (TRIM_MEMORY_RUNNING_CRITICAL while foregrounded, or TRIM_MEMORY_COMPLETE when the cached app is next in line to be killed). The warning callback fires with 'critical' and the instance stays reusable — recover with loadModel(). Ordinary lifecycle events such as locking the screen or pressing home (TRIM_MEMORY_UI_HIDDEN) never release the engine.

typescript
llm.setMemoryWarningCallback((level, usage) => {
  if (level === "critical") llm.unload(); // free multi-GB weights before the OS does it for you
});

Memory tracking

The tracker records getMemoryUsage() snapshots into a native-backed ArrayBuffer allocated via NitroModules.createNativeArrayBuffer(), keeping tracking data off the JS heap. It is a ring buffer: each snapshot uses 32 bytes (4 × Float64), and when the buffer is full the oldest snapshot is overwritten.

function createMemoryTracker(maxSnapshots: number = 256): MemoryTracker

createLLM({ enableMemoryTracking: true }) and useModel with enableMemoryTracking: true create one for you (as memoryTracker) and record a snapshot after each inference, load, unload, and reset.

MemoryTracker

The native buffer is preserved (not reallocated). */ reset(): void; /** Get a summary of memory usage statistics. */ getSummary(): MemoryTrackerSummary; }

Deterministic teardown

Do not rely on garbage collection to free multi-GB model weights — the JS GC has no idea a small wrapper object pins gigabytes of native memory. Free the engine explicitly:

MethodSemantics
unload()Releases the loaded model and conversation, freeing all engine memory, while keeping the instance reusable — call loadModel() again to reload.
close()Releases all native resources and permanently invalidates the instance. Call it when you are done with the LLM instance for good (useModel does this on unmount).
typescript
llm.unload();  // free the engine now; llm stays reusable
// …later…
await llm.loadModel(otherModelUrl);

llm.close();   // done for good; the instance is no longer usable

Errors

Failures carry machine-readable codes — branch on error.code instead of parsing messages.

LiteRTLMErrorCode

export type LiteRTLMErrorCode = | "MEMORY_ESTIMATE_EXCEEDED" | "MODEL_NOT_FOUND" | "MODEL_NOT_LOADED" | "ENGINE_INIT_FAILED" | "DOWNLOAD_FAILED";
CodeWhen it occurs
MEMORY_ESTIMATE_EXCEEDEDThe pre-flight estimate in loadModel() returned a 'critical' verdict and forceLoad was not set. Thrown as MemoryError.
MODEL_NOT_FOUNDReserved: the model file does not exist at the resolved path.
MODEL_NOT_LOADEDReserved: an operation that needs a loaded model ran before loadModel() succeeded.
ENGINE_INIT_FAILEDReserved: the native engine failed to initialize for the given model and config.
DOWNLOAD_FAILEDReserved: the model download could not be completed.

LiteRTLMError & MemoryError

/** Base error class for all typed react-native-litert-lm errors. */ class LiteRTLMError extends Error { readonly code: LiteRTLMErrorCode; constructor(code: LiteRTLMErrorCode, message: string); // name === "LiteRTLMError" } /** Thrown by loadModel() when the model likely does not fit. */ class MemoryError extends LiteRTLMError { readonly estimate: MemoryEstimate; constructor(message: string, estimate: MemoryEstimate); // code === "MEMORY_ESTIMATE_EXCEEDED", name === "MemoryError" }

MemoryError carries the full MemoryEstimate that triggered the refusal, so apps can show a useful message — or lower maxContextTokens and retry.

isMemoryError

function isMemoryError(e: unknown): e is MemoryError

The type guard checks e instanceof Error && e.code === "MEMORY_ESTIMATE_EXCEEDED" — not instanceof MemoryError — so it works across realms (e.g. when the error crossed a bundle or worker boundary).
