Manifest resolution

A model repo on the Hugging Face Hub can ship a litertlm_manifest.json describing every variant it contains. resolveFromManifest() reads it and returns the right .litertlm file, backend, config, and stream channels for the device it runs on.

What it solves

Without a manifest, an app hardcodes a file name, a backend, and a set of channel markers per model — three things that differ between variants of the same repo and between devices. Repos converted for LiteRT-LM ship a litertlm_manifest.json at their root describing every variant: the backends each file is verified to generate on, per-platform recommendations with evidence, sha256/size, thinking markers, and session defaults. This module reads it so apps stop hardcoding file names and channel markers per model.

The reader follows the manifest schema and is vendored from the reference TypeScript reader (john-rocky/hf-to-litertlm readers/ts, v0.2.0) with resolve renamed to resolveVariant, plus an optional signal and a status-carrying error on fetchManifest. Apart from fetchManifest, it is dependency-free and IO-free.

It never throws

resolveFromManifest() never throws. It returns null whenever the manifest can't help:

  • the repo ships no manifest (HTTP 404, the common case on the Hub today);
  • the manifest's schema is newer than this reader supports;
  • the fetch fails or is aborted (options.signal);
  • no variant lists an explicitly requested backend.

In every one of those cases, fall back to your normal loading path — no try/catch at the call site.

Note

The expected outcomes are silent: no manifest, an abort the caller asked for, an unlisted backend. Anything else — an unsupported schema, a body that is not a manifest, a network failure, a non-404 HTTP status — is reported with one console.warn line naming the reason. On React Native, LogBox shows console.warn in dev, which is too loud for the common path.

What a manifest looks like

Trimmed from a real repo's manifest — one cpu-only int4 file and one cpu+gpu re-export, each with its own platform recommendations:

litertlm_manifest.json
{
  "manifest_schema": "0.1.0",
  "repo": "litert-community/LFM2.5-1.2B-Instruct",
  "generated": "2026-08-24",
  "model": {
    "display_name": "LFM2.5-1.2B-Instruct",
    "context_length": 4096,
    "capabilities": {
      "thinking": { "declared": true, "channel": { "start": "<think>", "end": "</think>" } }
    },
    "session_defaults": {
      "max_output_tokens_min": 2048,
      "temperature": 0.3,
      "top_k": 40,
      "notes": "Reasoning model: keep maxOutputTokens ≥ 2048 so it can finish thinking."
    }
  },
  "variants": [
    {
      "file": "LFM2.5-1.2B-Instruct_int4.litertlm",
      "size_bytes": 736015744,
      "quantization": "int4",
      "backends": ["cpu"],
      "default_backend": "cpu",
      "recommended": [
        { "platform": "android", "device_class": "midrange", "backend": "cpu", "reason": "int4 decodes faster" },
        { "platform": "ios", "backend": "cpu", "reason": "verified path" }
      ]
    },
    {
      "file": "LFM2.5-1.2B-Instruct_int4_gpu.litertlm",
      "size_bytes": 736220768,
      "quantization": "int4 gpu re-export",
      "backends": ["cpu", "gpu"],
      "default_backend": "gpu",
      "recommended": [
        { "platform": "android", "device_class": "midrange-2023+", "backend": "gpu", "reason": "3-6x prefill" }
      ],
      "known_issues": ["iPhone Metal fails on this family — use CPU on iOS"]
    }
  ]
}

resolveFromManifest

export function resolveFromManifest( repo: string, options: ResolveFromManifestOptions = {}, ): Promise<ManifestResolution | null>

Fetch <repo>'s manifest from the Hugging Face Hub and resolve the right variant for this device.

typescript
const resolution = await resolveFromManifest("litert-community/LFM2.5-1.2B-Instruct");
if (resolution) {
  const llm = createLLM({ streamChannels: resolution.streamChannels });
  await llm.loadModel(resolution.url, { ...resolution.config });
}

platform defaults to this device's OS: the package export is a thin wrapper that injects React Native's Platform.OS as the default platform, so the core module never imports react-native. Pass platform yourself to override it.

typescript — the package export
export function resolveFromManifest(
  repo: string,
  options: ResolveFromManifestOptions = {},
): Promise<ManifestResolution | null> {
  return resolveFromManifestCore(repo, {
    ...options,
    platform: options.platform ?? manifestPlatformFor(Platform.OS),
  });
}

Example: load the resolved variant

A resolution carries everything createLLM and loadModel need. Spread config under your own overrides so your values win, pass streamChannels straight through, and log notes and reason — that is where the manifest tells you why it picked this file and what to watch out for.

typescript
import {
  createLLM,
  resolveFromManifest,
  GEMMA_4_E2B_IT,
} from "react-native-litert-lm";

// Don't let a startup resolve hang on a bad connection.
const controller = new AbortController();
const timer = setTimeout(() => controller.abort(), 5000);

const resolution = await resolveFromManifest(
  "litert-community/LFM2.5-1.2B-Instruct",
  { signal: controller.signal },
);
clearTimeout(timer);

if (resolution) {
  // "LFM2.5-1.2B-Instruct_int4_gpu.litertlm" · "gpu"
  // "recommended for android/midrange-2023+: 3-6x prefill"
  console.log(resolution.file, resolution.backend, resolution.reason);
  // "iPhone Metal fails on this family — use CPU on iOS", …
  resolution.notes.forEach((note) => console.warn(note));

  // streamChannels already merges the manifest's markers over the defaults,
  // so tool-call parsing survives a manifest that declares only thinking.
  const llm = createLLM({ streamChannels: resolution.streamChannels });
  await llm.loadModel(resolution.url, {
    ...resolution.config, // backend + session_defaults from the manifest
    maxContextTokens: 4096, // your own overrides win
  });
} else {
  // No manifest, or nothing it could resolve — your existing path.
  const llm = createLLM();
  await llm.loadModel(GEMMA_4_E2B_IT, { backend: "cpu" });
}

resolution.url is a plain HTTPS URL, so it goes through ModelRegistry like any other model — isCached(), resolveModel() with a progress callback, and deleteFile() all accept it.

Functions

resolutionFor

export function resolutionFor( manifest: Manifest, opts: ResolveFromManifestOptions = {}, ): ManifestResolution | null

Synchronous core of resolveFromManifest for an already-fetched manifest. Returns null when an explicitly requested backend is listed by no variant — fall back to your current (non-manifest) path in that case.

resolveVariant

export function resolveVariant( manifest: Manifest, opts: ResolveVariantOptions = {}, ): VariantResolution | null

Pick the variant and backend for a device, without deriving an LLMConfig or merging channels. Deterministic, and identical to the reference readers — see how a variant is chosen.

mergeStreamChannels

export function mergeStreamChannels( manifest: Manifest, defaults: StreamChannel[] = DEFAULT_CHANNELS, ): StreamChannel[]

Merge the manifest's declared channels over the package defaults, by type. createLLM({ streamChannels }) replaces the whole array, so handing it only the manifest's thinking markers would silently drop tool-call parsing; this merge keeps every default channel the manifest doesn't redeclare.

parseManifest

export function parseManifest(input: string | object): Manifest

Parse and validate a manifest body — a JSON string or an already-parsed object. Throws when the input is not a manifest, when the schema is outside 0.1.x, when the manifest has no repo, or when a variant lists no backends or no file. See schema versions for the exact messages.

fetchManifest

export async function fetchManifest( repo: string, revision = "main", signal?: AbortSignal, ): Promise<Manifest>

Fetch <repo>'s manifest from the Hugging Face Hub. resolveVariant() URLs follow the repo and revision fetched here — a fork whose copied manifest still names the origin repo downloads from the fork, not the origin. Throws on a non-2xx response (a ManifestFetchError carrying the status), an unsupported schema, or a failed/aborted fetch — resolveFromManifest turns all of those into null; call this directly when you want the error. signal aborts the fetch.

The URL it requests:

url
https://huggingface.co/<repo>/resolve/<revision>/litertlm_manifest.json

manifestFetchStatus

export function manifestFetchStatus(e: unknown): number | undefined

The HTTP status carried by a ManifestFetchError, or undefined for any other error. Use it to tell a missing manifest (404) from a gated repo (401/403) or a Hub outage (5xx) after a direct fetchManifest call.

typescript
try {
  const manifest = await fetchManifest("litert-community/LFM2.5-1.2B-Instruct");
  const resolution = resolutionFor(manifest, { platform: "ios" });
} catch (e) {
  if (manifestFetchStatus(e) === 404) {
    // The repo ships no manifest — expected on most Hub repos today.
  } else if (manifestFetchStatus(e) === 403) {
    // Gated repo: the user needs to accept the model's terms.
  }
}

thinkingMarkers

export function thinkingMarkers(manifest: Manifest): ThinkingChannel | undefined

The model's declared thinking markers (exact strings, whitespace included). undefined when the manifest declares no thinking channel.

Whitespace is significant

Markers are used verbatim. A manifest declaring "<think>\n" / "\n</think>" resolves to exactly those strings, and the stream parser matches them including the newlines — that whitespace is part of the marker, not formatting.

declaredChannels

export function declaredChannels(manifest: Manifest): DeclaredChannel[]

The bundle's full declared channel set (manifest 0.1.1+); empty for 0.1.0 manifests.

Behavior notes

Schema versions

parseManifest() accepts manifest_schema values matching 0.1.x and rejects everything else. 0.1.0 manifests declare thinking markers only; 0.1.1 adds capabilities.channels, the full declared channel set. The validation failures:

error messages
not a litertlm_manifest.json (missing manifest_schema or variants)
unsupported manifest_schema <version> (reader supports 0.1.x)
manifest has no repo (schema requires it) — download URLs need one
variant <file> lists no backends (schema requires minItems: 1)
variant with backends [<backends>] has no file (schema requires it)

Through resolveFromManifest, each of these becomes null plus one console.warn line. A manifest whose schema is newer than 0.1.x is treated the same way — the reader refuses to guess at a shape it does not know.

How a variant is chosen

The manifest v0.1 algorithm, deterministic and identical to the reference readers:

  1. An explicit backend request is a filter, not a score: only variants listing it compete, the result keeps that backend, and resolveVariant() returns null when no variant lists it — it never substitutes another backend.
  2. A variant with a recommended entry matching the requested platform wins; matching device_class too ranks higher. When a backend was requested, only recommendations naming that backend count.
  3. Otherwise the smallest variant (by size_bytes), on the requested backend (else its default_backend, else the first listed backend).

Ties break toward the smaller file, and a variant without size_bytes sorts last. The reason string on the resolution records which branch fired:

Situationreason
Platform + device class matchedrecommended for android/midrange-2023+: 3-6x prefill
Platform matched, requested class did notrecommended for android (no budget-2019 entry; using the midrange recommendation): int4 decodes faster
Backend requested, no recommendation matchedsupports requested backend gpu
Nothing matchedfallback: smallest variant
Note

An unmatched deviceClass never silently upgrades the pick: the resolver falls back to a platform-level recommendation and says so in reason, naming the class it actually used.

Backend preference and fallback

Passing backend filters the candidate set. If no variant in the repo lists that backend — asking for "npu" in a CPU-only repo, say — the resolution is null, silently, and you fall back to your own loading path. Nothing is substituted.

Without a backend request, the backend comes from the winning recommendation; failing that, from default_backend when the variant's backends list contains it; failing that, from the first listed backend. The resolver never returns a backend absent from the variant's verified backends list.

Warning

A recommendation is evidence about a family of devices, not a guarantee about the one in your hand. Manifests carry the counter-cases in known_issues — for example iPhone Metal fails on this family — use CPU on iOS — and those strings arrive in resolution.notes. Read them before shipping a GPU default.

Platform defaulting

The package export injects Platform.OS as the default platform. android, ios, macos, and windows are forwarded as-is, so react-native-macos and react-native-windows keep their recommendations. An OS no manifest names — web, native — forwards nothing, which means no recommendation can match and the smallest variant wins. "linux" is a valid ManifestPlatform but is never injected; pass it explicitly if you need it.

What lands in config

resolutionFor() maps the session_defaults keys it knows into an LLMConfig fragment:

session_defaults keyLLMConfig fieldMapping
—backendThe resolved backend, always set.
max_output_tokens_minmaxOutputTokensA floor, never a cap: max(1024, max_output_tokens_min), where 1024 is the package default.
temperaturetemperatureCopied when it is a number.
top_ktopKCopied when it is a number.
top_ptopPCopied when it is a number.

The floor exists for reasoning models that need room to think before answering — 2048 output tokens, say. Caller overrides win via { ...resolution.config, ...userConfig }, so if you take a value from the user, apply max(userValue, floor) yourself.

How stream channels merge

createLLM({ streamChannels }) replaces the whole channel array. Handing it only the manifest's thinking markers would silently drop tool-call parsing, so mergeStreamChannels() layers the manifest's channels over the defaults, keyed by event type:

  • Start from DEFAULT_CHANNELS — <tool_call>…</tool_call> for toolCall and <thinking>…</thinking> for thinking.
  • For each declared channel (0.1.1+), map it to an event type: is_reasoning, or a name of thought or thinking, maps to thinking; a name containing tool maps to toolCall. Anything else is skipped — this package has no event type for it yet.
  • A mapped channel replaces the default entry of that type; every type the manifest doesn't redeclare keeps its default markers.
  • Whenever the declared list doesn't cover thinking — a 0.1.0 manifest declaring no channel set at all, or a 0.1.1 manifest declaring only a tool channel — the capabilities.thinking markers fill in, and the default toolCall entry survives untouched.

Aborting the fetch

Pass options.signal so a resolve at startup can't hang on a bad connection. The signal is forwarded to fetch, and an aborted fetch resolves to null with no warning — the caller asked for it, whether that was a timeout or an unmount.

typescript
useEffect(() => {
  const controller = new AbortController();
  resolveFromManifest(repo, { signal: controller.signal }).then((r) => {
    if (r) setResolution(r);
  });
  return () => controller.abort();
}, [repo]);

Revisions

revision pins both the manifest fetch and the download URLs it produces, so a resolved URL always points at the same tree the manifest was read from. fetchManifest() stamps the fetched revision onto the manifest object; resolveVariant() uses that, unless opts.revision overrides it. With neither, URLs fall back to main.

What is not derived from the manifest

Two knobs are deliberately left alone:

  • context_length does not seed maxContextTokens. They look like the same number but are different knobs: the manifest value is what the model can address, the package default is a memory ceiling, and quietly raising it to 128K on a phone is the OOM the pre-flight check exists to catch. contextLength is on the resolution for apps that want more, knowingly.
  • streamToolCalls stays off even when the manifest declares a tool channel. A declared channel says the model can emit tool calls, not that this app wants to handle them, and switching engine behavior on as a side effect of "resolve a URL" would surprise a caller.
